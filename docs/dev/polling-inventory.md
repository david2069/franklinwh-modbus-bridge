Nothing was run, and no device or service was contacted. Line numbers are from that commit. Library lines are from the installed copy in `venv/`.

Defaults used for "per hour": one real gateway, `poll_interval` 10 s (`config/settings.py:42`, `addon/config.yaml` `poll_interval: 10`, DB default `store/db.py:349`), timeout 10 s, single-phase, one battery, MQTT enabled, no solar location, no NEM region, one HA instance. ## Summary

**The aGate :502 session pattern.** Each real gateway uses **two TCP sessions to :502 at once**, plus short extra connects:

- **Session A (library, pysunspec2 socket).** It is opened by `controller.connect()` and then kept open between polls. Model reads reuse it (`sunspec2/modbus/client.py:84-103` only opens a socket when none is open). But two library helpers call `client.connect()` on every poll. That call closes the open socket and opens a new one (`sunspec2/modbus/modbus.py:599-614`): `_read_extension_solar` (`controller.py:749`) and `read_native_mode` (`controller.py:893`). So session A is **torn down and reopened twice per poll**, which is 720 new TCP connections an hour. This matches the measured "at least 11 distinct connections in 60 s" (design doc C6), and corrects C1's "one connection per model read".
- **Session B (bridge, pymodbus `_vreg_client`).** This is a second, long-lived TCP session for the vendor registers 15000-15039, 15510-15513 and 16000-16002 (`modbus/poller.py:772-791`). It stays open across polls, alongside session A. It is closed only when a vendor read fails or the poller stops. A poll-level reconnect does not close it.
- **Bare connects.** `HealthChecker` opens and closes a TCP connection to :502 **every 60 s** per gateway (`gateway/health.py:27,91`, `gateway/net_probe.py:50-55`). Buttons can open more.

**Requests per poll (every 10 s, all inside the gateway's `modbus_lock`).** There are 15 Modbus requests in total. Session A carries 12: M713, M714, M701 (two requests, because it is 155 registers), M502, M714 again, a reopen, 15500×14, 16000×1, M704, M715, a reopen, 15507×3, then M714 a third time. Session B carries 3: 15000×40, 15510×4, 16000×3. At defaults that is **360 polls, 5,400 requests and about 780 new TCP connections an hour** per gateway (720 reopens plus 60 probes). There are no writes in steady state.

**On every connect** (twice at bridge start, then on each poller-level reconnect), `controller.connect()` does several things. It runs a full SunSpec scan. It reads M702 (rating discovery). It runs `_test_extension_writability()`, which **writes 15507 (operating mode), 15508 and 15509 (reserves) with test values, then writes the originals back**. That is up to 12 requests, each on a fresh TCP connection. Last, it reads M704 to look for an orphaned dispatch. Nothing in the bridge reads the result of the write test.

**Reconnects in practice.** The poller's own reconnect-with-backoff (5 s, doubling to 60 s) runs only when a poll returns no points at all. But each sample includes the cached startup points (`poller.py:498`), and the library read methods swallow their errors and return `{}`. So after the first good start, a poll is never "error" and the poller never reconnects. Recovery is left to the library's `_with_retry` (`controller.py:383-408`). On a connection error, each of the four retried read methods does `reconnect()`: it closes the socket, sleeps 1 s, opens a new TCP connection and runs a full rescan, without the write test.

## Findings, by risk

1. **Every connect writes the operating mode and both reserves.** `controller.connect()` runs `_test_extension_writability()`. It writes 15507 (mode) and 15508/15509 (reserves) with test values, then writes the originals back, opening a new TCP connection per request. That happens twice at each bridge start and again on every poller reconnect. If the restore fails, the aGate is left in the wrong mode or reserve. Nothing in the bridge reads the result (**no consumer found**). `controller.py:141,178-325`; called from `poller.py:199` and `instance.py:249`. Suggestion: add a library option to skip the test, and pass it from the bridge.
2. **Two concurrent :502 sessions per gateway.** Session B (`_vreg_client`) stays open while session A reopens around it. The aGate's client limit is unknown (design doc U1). `poller.py:772-791`. Suggestion: move the three vendor reads onto session A's socket, or onto one library-owned client.
3. **Session A is reopened twice per poll (720 TCP connects an hour).** `_read_extension_solar` and `read_native_mode` call `client.connect()`, which closes the live socket and opens a new one. `controller.py:749,893`; `sunspec2/modbus/modbus.py:599-614`. Suggestion: connect only when `client.socket` is None (a library change), and drop `read_native_mode` (see 6).
4. **Bare TCP connect to :502 every 60 s.** `HealthChecker` opens and closes a connection that sends nothing, as Direct Connect's #221 does. It tells us nothing the poller doesn't. `gateway/health.py:27,91`; `net_probe.py:50-55`. Suggestion: derive `health` from the poller's last good sample, and probe TCP only after the poll has failed.
5. **The library's timer releases a dispatch without the bridge's lock.** With a time limit, `send_command(duration_s=…)` starts a `threading.Timer` that calls `reset_control_state()` with no `modbus_lock`. It can interleave Modbus frames with a poll on the same socket. The bridge watchdog releases the same command, under the lock, within 5 s. `command_handler.py:494,511`; `controller.py:1490-1503`. Suggestion: pass `duration_s=None` and rely on the bridge watchdog.
6. **Duplicate reads in every poll.** 15507-15509 are read twice (`read_native_mode` plus the 15500×14 block). M714 is read three times (battery, solar, `_read_extra_points`). 16000 is read twice (library plus session B). That is 4 extra requests a poll (1,440 an hour) and one of the reopens. `poller.py:57,750,844`; `controller.py:484,696,893`. Suggestion: take the mode and reserves from `_read_extension_solar`, drop `m714.read()` in `_read_extra_points`, and drop range 3 from the vendor read.
7. **The poller's reconnect path is effectively dead, so recovery is a rescan per read method.** Cached startup points keep every sample non-empty (`poller.py:498,577`), and library methods return `{}` on failure. So the poller's backoff never runs. During an outage, each 10 s poll can trigger up to four `reconnect()` calls, each with a 1 s sleep, a new TCP connection and a full scan (`controller.py:352-408`). Session B is never closed on these paths, and the old session A socket is replaced without `close()`. Suggestion: judge quality from the live reads only, and close both sessions before reconnecting.
8. **Startup reads everything twice.** `_init_and_poll` connects, reads, disconnects, then the poller connects again: 2 scans, 2 write tests, and M1/M701/M702 read 2-3 times. `instance.py:247-321`; `poller.py:236-295`. Suggestion: hand the first session to the poller.
9. **Explorer "Read model" can trigger a full connect.** When `controller.dev` is None, it calls `controller.connect()`, which includes the write test (1). `api/admin.py:325-327`. Suggestion: refuse when the poller is not connected.
10. **MQTT republishes every value every poll.** That is 64-79 retained publishes per 10 s per gateway (~23-28k an hour), mostly unchanged. `mqtt_publisher.py:806-830`. Suggestion: publish on change, with a periodic refresh (for example 5 min).
11. **The Schedule tab polls HA's service list.** It calls `GET /api/services` on every HA instance every 20 s while the tab is open. `schedule_tab.js:351`; `ha.py:510-516`. Suggestion: load notify targets once per tab open.
12. **HA seed is fetched twice at start.** REST `/api/states` and then WebSocket `get_states` return the same data. `ha.py:430` and `ha.py:308`. Low cost.
13. **UI loops ignore tab visibility.** The 10 s app-shell refresh (4 requests) runs in every open tab, hidden or not. It never reaches the device. `app.js:652`. Suggestion: pause when `document.hidden`.

Calls with **no consumer found**: the extension write test (finding 1). The `_check_orphaned_vpp` M704 read only writes a debug log. The HA REST seed at start (finding 12) is superseded by the WebSocket seed.

## Interference with the other bridge

- **Shared resource.** Both bridges reach the same aGate. Direct Connect uses :9000 and, optionally (its #221), bare TCP connects to :502 every 30 s. We use :502 heavily: 2 sessions, about 780 connects and 5,400 requests an hour. We touch :9000 only when someone runs Diagnose or `bridge diagnose` (one bare connect each, `diagnostics.py:62`, `cli.py:159`).
- **Calls that collide on :502.** Every row in our :502 table competes with Direct Connect's :502 probes. The worst are our 720 session-A reopens an hour (2 per poll), the long-lived session B, our own 60 s bare probe, and the reconnect rescans. Direct Connect's probe adds about 120 connects an hour to the same listener.
- **If the aGate allows only one Modbus client.** We already break that limit by ourselves: session B is open while session A opens. Then one of three things happens:
  - The aGate refuses new connections. Our reopens or Direct Connect's probes fail at random. Direct Connect would report :502 down while we are healthy.
  - The aGate drops the older connection. Each Direct Connect probe can cut our session A or B mid-poll. That gives a "stale" sample, 0xFFFF values (already seen, `poller.py:413-427`), or a library rescan. A poller-level reconnect would then repeat the mode and reserve write test (finding 1).
  - The aGate serialises clients. Every probe adds latency to our 10 s poll.

  Our 60 s probe does the same to Direct Connect's :502 probe, but not to its :9000 traffic.
- **Advice for running both.** The policy is "one Modbus client per aGate" (`docs/install-lifecycle.md:194`). Until the session work (findings 2-4) is done, Direct Connect's :502 probe should stay off while this bridge polls the same aGate. Our `HealthChecker` probe should also go, or wait for a failed poll.
